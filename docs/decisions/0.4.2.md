### B11 · 2026-10-25 · Brightness as the Portal's slider counts it: straight
Status: on the Portal 2026-10-25, the owner: "it is correct now. 10% no tint." The first try
(below, *Rejected*) went the wrong way by the owner's eye. B11.2's snapping not clicked yet.

**Ask** (owner): "The brightness slider is incorrectly scaled. On system brightness, around 9%
is where the green tint comes into play. In our launcher, the min is 8% and around 35% is where
the green tint becomes obvious."
**Why it was off**: the slider put Android's 0–255 `screen_brightness` through a 2.2 gamma, so
value 1 showed as 8% and value 25 as 35%. The 1..255 setting spans the display's 0..1 level
linearly (`BrightnessSynchronizer`; on the Portal `dumpsys display` gives min 0.0, max 1.0, and
190 reads back as 0.744), and the owner's two marks meet exactly on that straight scale: our old
35% is value 25, which is 9% of 0..1, where the owner sees the tint start on the Portal's slider.
So the Portal's slider shows the level straight.
**What**: B11.1 the slider's percent is the setting straight, (value − 1) / 254: 0% at value 1,
the same number as the Portal's slider. B11.2 (owner: "5% steps on both volume and brightness"):
brightness steps land on the 5% marks, so a level set elsewhere (22%) steps to 20 or 25.
Volume stays one level a step: the Portal's media stream has 15 levels (6.7% each, `dumpsys
audio`) and apps can set only whole levels, so 5% steps would sometimes not move it.
**Rejected**: AOSP's slider curve (`BrightnessUtils`, HLG), the first try: it put value 25 at
53%, further off than the gamma; the Portal's slider doesn't use it.

### D36.1 · 2026-10-25 · Home dims while the dock has focus (F36)
Status: on the Portal 2026-10-25, the owner: "This looks good"; released in 0.4.2.

**Ask** (owner, a FeatureBoard card, then in chat): "Defocus the home tiles when using the dock
icons, similar to when modifying a tile using Triangle." The card: "a darker render on the home
items when the dock is getting focused on".
**What**: while the zone is the dock, Home gets the options sheet's 0.6 scrim (background color,
on the HERO_FADE timing) over the backdrop, hero and row; the name band and the category label,
drawn above it, fade by as much. Only the bottom row stays: the dock and its hints (they are
the dock's buttons). The status cluster stays too, as over a sheet.
**How it got there** (owner, 2026-10-25): first the row alone faded to about 40% ("feels too
much"), then halfway, about 62%; then "the same as the tile edit, where only the dock is in
focus", which is this. The big name keeps the accent on the dock too (it went muted
off the row, which under the scrim read as white; owner: "same color throughout").
Then "reduce the dock when it's not focused as well": while the row has focus the dock's
buttons fade by as much (0.4), per draw (`ModulateAlpha`), since a layer the dock's size would
clip the ring and the name above while fading back in. Its hints stay bright either way.

### B12 · 2026-10-25 · Portrait letterboxed; a crash on Home's resume
Status: both run on the Portal 2026-10-25 (portrait by `user_rotation 3`, then back to 0).

**B12.1 Ask** (owner, while the release was tested; the Portal had landed in portrait with
auto-rotate on): "We need a fall back if the device is in portrait mode." In portrait Home drew
the landscape layout into 600 × 1067 dp: the name cut off, the hero squashed at the top, one tile.
**What**: in a window taller than wide, the root draws Home in a box the screen's own shape
turned sideways (16:9 on the Portal), across the width and centered, the background color above
and below, clipped; the canvas density is measured from that box, so the scaling fits it as on
any landscape screen (0.56 on the Portal). Sheets, All apps and the quick panel come with it.
**Rejected** (owner picked the letterbox): drawing Home turned 90° (full size, but the status
bar and other apps stay portrait, and which way to turn depends on the rotation); a real
portrait layout (portrait stays a non-goal). Forcing landscape can't work: Android 16 ignores
`screenOrientation` at 600 dp and up (`gotchas.md` *Rotation*).

**B12.2** (found by the release's R8 run): `HomeHoldSwitch.restricted` reads the
access-restricted-settings app op, which the Portal's Android refuses without MANAGE_APPOPS,
even for the app's own uid: a SecurityException, not the IllegalArgumentException caught. It is
read only while standby's service is off, so the owner's Portal (service on) never hit it, but
a fresh install or a force stop crashed Home on every resume, 0.4.1 included. Now a refusal lets
the install source decide, as for an unset op.
