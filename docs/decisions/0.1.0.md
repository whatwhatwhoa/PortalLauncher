### D9.1 · 2026-10-25 · Hero reflection (F9, T9.1)
Status: as built 2026-10-25, owner to confirm (*V-reflection*). Seen on the device only as far
as the build installing; no app without a scene was focused (the owner was using the Portal).

**Ask** (owner): "keep the hero gradient but also add a blurred/darken mirror, so like a soft
windy moonlight reflection", for the space under the band when an app has a hero but no scene.
**Why this shape**: the mirror line sits at 80% of the band (218 dp), inside the band's own fade,
so the two meet where both are faint and there is no horizon line; a mirror at the band's edge
put a bright strip against the band's fully faded bottom. Blurred 3 dp across and 10 dp down so
it streaks like light on water rather than a soft copy; the slow sway (two sine waves, 9 s loop,
up to ~13 px, growing away from the line) is the "windy" part, and it is blurred after the sway
so the ripples stay soft. Darkened and cooled toward blue in dark themes ("moonlight"); in light
themes only desaturated, since a dark patch on a light page reads as a smudge. Gone by 400 dp,
above the dock and hints.
**A switch**, *Hero reflection*, on by default, like the other three effects, so the owner can
judge it against its absence.
**Cost**: the ripple redraws one layer each frame while Home shows a band; the focus pulse
already redraws Home continuously, so it adds no new wakeups. With animations off it is still.
**Rejected**: a reflection of the whole screen (the carousel would mirror too and fight the tile
depth); faking it with a gradient of the hero's colors (not a reflection; Hero glow already does
color).

### D10.1 · 2026-10-25 · Starting categories (F10, T10.1)
Status: as built 2026-10-25, owner to confirm (*V-starting*), especially (a) and (b) below.

**Ask** (owner): "ship it with the most popular apps in their default categories, so if users
have those apps, it'll place there. After that, newly installed apps go into all apps and don't
populate home."
**Built**: a table of 117 package names (emulators, frontends, stores and remote play →
Games; video, music, books → Entertainment; chat and social → Social; browsers, the system's and
Google's everyday apps, file tools → Utilities). An app's start is the table, then its
manifest's category, then Utilities. The launcher stamps the time it first sorts the apps
(`apps.sortedAt`, set on the first run of this version, so the owner's current apps all count
as there from the start); an app first installed after that starts in **All apps only**, off
Home, until the owner places it. Category… gained an *All apps only* row, so an app can also be
taken off Home, and a placed new app can be put back.
**Why first install time**: `firstInstallTime` survives updates, so an updated app never jumps
to All apps; no list of known packages has to be stored. A reinstall counts as new.
**Why the table wins over the manifest**: manifests are often empty or odd (Chrome declares
itself social); the table is the curated answer. Only package names known for certain are in
it; a wrong one would only never match.
**Open**: (a) an unknown app that is there at the first run still starts in Utilities (as
before), not All apps only: keeps a new user's Home from starting nearly empty. (b) A table app
installed *later* also goes to All apps only, read literally from the ask. (c) For the owner,
Chrome moves from Social to Utilities (the table), so Social may disappear if it held only
Chrome. Any to change?

**Ask** (owner): "use our launcher icon + gear or something. Too many gears." The dock had
Android's Settings (a gear) next to ours (a gear), and the quick panel has one too.
