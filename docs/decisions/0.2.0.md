### D19.1 · 2026-10-25 · Hold Home for standby (F19)
Status: built 2026-10-25; the owner's first try: the hold works, but "really dark" and "registers
any type of inputs, including screen and joystick"; second build (owner's brightness, brighter
text, buttons only) looked good; then the clock halved and everything a fifth fainter, for
power (owner, 2026-10-25). Owner's third try: the triggers still woke it and any mix of buttons
did; now only the same button four times, triggers swallowed (built 2026-10-25, not yet seen).

**Ask** (owner): "long press home button to lock screen. When single click, a hint comes up and
displays for 0.5 or so seconds." Mid-session, after trying LineageOS's sleep action: locking
"kicks you out of the launcher" (and wakes into the Portal's anti-accidental-press guard), so
instead "an always on display, standby, taking a break but not locking the screen/OS". It must
work on stock Android too, not only LineageOS. Leaving standby: "any button 4 times", later
the same button four times, the triggers not counting.
**Why an accessibility service**: Android handles the Home key itself; the Home app only gets an
intent on release, and a hold goes to Circle to Search (`gotchas.md`). LineageOS's own hold
action works (tried: 7 = sleep) but only offers system actions and exists only on LineageOS.
The service sees the key first everywhere; it hands short presses back as Android's Home, so
Home behaves as before, and reads nothing else. Off until the owner turns it on; the settings
row opens the page. The hint shows only while the service is on, so it never promises a hold
that does nothing.
**Why these numbers**: four presses of one button within 2 s of the first, so a bump in a bag,
which presses whatever it presses, doesn't wake it; another button starts the count again at one;
touches, sticks and triggers never count (owner); rings show the count so a press never seems
lost. The triggers needed their buttons swallowed too: the Portal's controller sends each as an
axis (ABS_Z/RZ) and as BTN_TL2/TR2 (`getevent -lp`), and only the axis was ignored at first. A
D-pad push counts as its direction's key, so pushing up four times wakes and rolling round the
pad doesn't. The owner's brightness (5% was too dark) and a minute's drift for the OLED. 0.6 s for the hint: the owner's half second plus the fades.
**Rejected**: lock or sleep (the ask changed); the assistant role (a hold here starts Circle to
Search, not the assistant); a lock screen of our own (Android doesn't let a launcher replace it).
**Side effect**: LineageOS's hold action on the owner's Portal is now 0 (nothing), set while
trying; it was unset (Circle to Search). With the service on it doesn't matter.

### D12.1 · 2026-10-25 · Renaming and adding categories (F12)
Status: built 2026-10-25, the layer and edit mode seen by the agent on the Portal; the owner's
hand check is *V-categories-edit*.

**Ask** (owner): renaming or adding categories, the fixed five first (`M5-categories.md`). The
owner's answers: edit from the categories layer; everything but Favorites can be renamed, moved
or deleted, Favorites renamed only; a deleted category's apps go to All apps only; no limit on
how many. Mid-build: a + Edit hint in the layer; then "hide the new category button, keep it
clean and edit mode separate"; then "apps can show in multiple categories as well".
**What**: a category is an id and a name (the enum is gone). The built-in five keep their old
names as ids, so the stored moves and the last category read unchanged; a new one gets a
made-up id ("c" + time), never reused, so no old choice points at it. The list is stored
(`categories.list`), Favorites forced first. Edit mode is a second state of the layer, not a
screen: the names are where they are edited (WYSIWYG). An app's categories are a set
(`categories`: "key<TAB>id,id"); one-id lines from before read as a set of one.
**Why these**: Rename, Move and Delete beside the name rather than in a side panel: the name
being changed stays in view and the layer keeps its look. Delete takes two A's like the
settings' undoable rows. A new category is kept only once named, so backing out leaves nothing.
B keeps a typed name, as B keeps the art search's words. An empty category is shown only in
edit mode, with a note on how to fill it, since Home has no row to show for it.
**Side effect**: the Category… page scrolls now, so its rows got room inside the scroll for the
ring (the first build clipped it: the owner's screenshot `concepts/screenshots/2026-10-25-cutoff.png`).
**Rejected**: a Launcher Settings page (owner chose the layer); a cap on the count (owner: none,
the layer scrolls); typing a name with the D-pad on our own keyboard (Android's works).

### D18.1 · 2026-10-25 · Updates from GitHub (F18)
Status: built 2026-10-25; ran on the Portal in a side-by-side test copy against a laptop
stand-in for GitHub; the owner's own launcher can't use it yet (*Limits*).

**Ask** (owner, the card): "Able to update via Github." No more than that; the agent chose the
shape below and put the open points to the owner.
**What**: an *Updates* row at the end of Launcher Settings → System. It asks GitHub's
`releases/latest` when the panel opens and says what it found; A on "Install 0.2.0" downloads
the release's APK, checks it and installs it over the running launcher, data kept.
**Why this shape**: the panel is where the version already shows, and asking only when it opens
keeps Home calm (no badge, no background job, no network the owner didn't cause). The checks
before installing (same package, higher versionCode, same signing key) turn Android's late,
vague install failure into a plain word on the row. Self-update needs no Android confirm on 12
and later, so it is one A after the one-time *Install unknown apps* grant.
**How it was tried** (2026-10-25): a debug copy under `.check`, versionCode 1, against
`update.url` served from the laptop through `adb reverse`; the row said "Install 0.1.1", A
opened the grant page, granted (by appops, to the copy only), A downloaded and installed:
versionCode 2, data kept, the launcher restarted, its installer of record itself. Play Protect
asked to scan the unknown APK first; *Install without scanning* let it through (nothing was
sent to Google). An older APK served as "0.1.2" was refused with "Not newer". The copy was
uninstalled after. Not tried: GitHub itself (the repo is private, so it answers 404: "None
published"), a release-signed update.
**Limits**: (1) Nothing to find until the repo is public and a release has an APK attached.
(2) The owner's daily build is debug-signed and will read "Signed differently" for every
release: updates reach it only after the owner moves to the release build, which means
uninstalling (Android won't change an app's key), so favorites, dock and art would need
moving first. (3) Each release must raise `versionCode`, or it reads "Not newer".
**Rejected**: a daily background check with a dot on the gear (more than the card asked, and a
network call the owner didn't make; easy to add if wanted); sending users to the GitHub page
in a browser (downloading and installing by hand on a controller is what this saves); Obtainium
or another updater app (one more app to set up).
